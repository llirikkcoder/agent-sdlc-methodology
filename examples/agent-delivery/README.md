# Пример: поставка изменений параллельными агентами (anchor)

Модель описывает цикл поставки (docs/03) так, как он устроен в [anchor](https://github.com/llirikkcoder/anchor). anchor — плагин Claude Code: одна тема — одна вкладка, одно git-дерево и один якорь в трекере. Здесь методология описывает собственный цикл поставки, тогда как два других примера описывают цикл исполнения.

Слой 5 сверен с кодом anchor на коммите `c491bc7` (26.10.2026, после PR #9): `make drift-anchor ANCHOR_REPO=<путь к anchor>` даёт 0 расхождений. Негативная проверка: переименованные `cmd_add` и `check_gates` и удалённый `scripts/heavy` пойманы как `stale`.

## Что откуда взято

| В модели | В anchor | Замечание |
|---|---|---|
| `Topic` и её состояния | якорь в трекере; `.anchor/state.json` (`working/waiting/stuck`) и `.anchor/done.json` (сделано или не сделано) | состояние «застрял» объявляет сам воркер; один признак — не основание (C007) |
| `topic_start` | постановка, `anchor-queue add/run` | человеческий шаг `set_topic` — это и есть согласие на слияние (ADR-019) |
| `topic_delivery`, шаг `merge_own_pr` | `skills/anchor/workers.md` «Поставленная тема = сделать И слить» | **гейта человека нет**: воркер сливает сам по гейтам, ровно проверенный коммит |
| `exception_merge` | `anchor-merge` оркестратора | пара сводится по гейтам без «да»; миграция и правка ядра модели идут через условный гейт по C005 |
| C010 «миграция только после копии» | `anchor-merge --migration … --backup …` | |
| `topic_close` | `/anchor-done` | ветка не удаляется, а переименовывается в `merged/…` |

## Что показывает этот пример в ядре

- **ADR-019 в данных.** Шаг агента со слиянием (`write_compensable`, компенсация — `revert_merge`) не требует гейта. Валидатор это принимает, потому что слияние кода не `system_level` и не `write_irreversible`. Исключения выражены двумя способами: ограничением `pre_check` у воркера (C009, «не сливать самому») и условным гейтом по ограничению у оркестратора (C005).
- **Возможности вида `cli` со сверкой по коду.** `drift --repo` проверяет пути скриптов и функции Python в них. Три привязки подтверждены документами, а не кодом (`sync_main`, `merge_own_pr`, `close_topic`: это `git`, `gh` или шаги команды), поэтому валидатор честно предупреждает: «evidence не code».
- **Неподтверждённое ограничение уровня high.** C012 («красный main останавливает следующие слияния») в anchor не реализовано: смысловой конфликт двух тем ловит только следующая проверка. drift показывает его как INFO, а в `--strict` как WARN; ERROR оно не даёт (ADR-017).
- **Журнала событий в цикле поставки нет** (ADR-019 п. 6). След — итог в якоре, запрос на слияние и `result.json` прогона гейтов. `events.sample.json` показывает тот же ход событиями, для сравнения:
  - тема t42 слита воркером без `HumanGateRequested`;
  - тема t43 с миграцией прошла гейт C005;
  - тема t44 получила отказ по C002: ветка сдвинулась после проверки.

## Стык с методологией

- **Гейты.** В репозитории с моделью `.anchor/gates` включает проверку модели: `make check` или `validate`, `drift`, `purity` по отдельности. Пример — `.anchor/gates` в корне этого репозитория.
- **Дыры как задачи.** `python3 tools/drift.py <модель> --json | python3 tools/holes_to_tasks.py - --emit bd` печатает команды `bd create` по одной на дыру, с ключом `drift:<причина>:<процесс>:<шаг>:<возможность>` во `--external-ref`. Уже заведённые ключи пропускаются через `--skip-keys`. Инструмент только печатает и в трекер не пишет.

## Регулярные задачи и ступень `on_edit`

- `scheduled_drift` (planned) — по расписанию и после слияния: `drift --repo` со снимком, затем задачи только по новым дырам (C013, ключ drift).
- `post_merge_docs` (planned) — после слияния агент сверяет документацию с изменением и, если она отстала, ставит тему на её обновление; правка сама проходит гейты и самослияние.
- Обе рутины в anchor пока не настроены. Поэтому процессы `planned`, привязки `planned`, а drift показывает их как INFO.
- `checks[]` со `stage: on_edit` — ограда воркера (`worker-guard`) и ловушки Bash (`bash-pitfalls`, пока в режиме счёта). Это проверки в момент действия агента, раньше гейтов слияния.

## Не подтверждено

- Схема хранилища трекера (`anchor_tracker`): помечена `unconfirmed`.
- C012: в anchor нет механизма остановки слияний при красном main.
- Компенсация `revert_merge` не автоматизирована (`planned`).
