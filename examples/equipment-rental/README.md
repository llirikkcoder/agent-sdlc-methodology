# Пример: пункт проката оборудования (`equipment_rental`)

Бизнес без кода, оцифрованный классами (ADR-021, `docs/08-digitization.md`). Источник — `model.py`; пять файлов слоёв собраны из него и сверяются с ним в `make check` (`make described`). Если поправили `model.py`, пересоберите слои:

```bash
python3 tools/digitize.py build examples/equipment-rental/model.py --out examples/equipment-rental
python3 tools/digitize.py map examples/equipment-rental --out /tmp/rental-map.md      # карта процессов
make twin                                                                            # две сквозные аренды на двойнике
```

## Что описано

| Слой | Содержание |
|---|---|
| 1 | Роли: менеджер (утверждает), сотрудник выдачи, ИИ-агент проката, учётная система. Ограничения C001–C006: порог возврата залога 50 000 ₽ (gate с threshold); акт и залог до выдачи; запрет пересекающихся броней; удержание залога только через менеджера; проверка после ремонта (`unconfirmed`, high); решение по залогу у каждой закрытой аренды (post_check) |
| 2 | Абстрактная база `Tracked` (id, created_at) и четыре сущности: `Equipment` (автомат из шести состояний), `Booking` (шесть), `Deposit` (держится → возвращён / удержан), `Inspection`; шесть доменных событий |
| 3 | `booking_request`, `equipment_issue`, `rental_return`, `damaged_return` (наследник `rental_return`: заменены шаги `settle` и `release`), `overdue_check` (по расписанию), `repair_cycle` (planned) |
| 4 | 17 возможностей: три чтения, `llm_step` для оценки повреждений по фото, два необратимых действия (возврат и удержание залога), приём залога — `write_compensable` с компенсацией возвратом |
| 5 | Кода нет: все 17 привязок `planned`, `as_of` — 27.10.2026 |

## Что пример показывает в ядре

- **Описание классами без потерь.** `decompile` любой из моделей и обратный `build` дают те же файлы. Этот пример написан сразу классами.
- **Наследование процессов.** Возврат с повреждением — тот же возврат, у которого другие решение по залогу и судьба единицы. Шаги не копируются.
- **Порог из атрибута.** `condition=Deposit.amount > 50000`: ниже порога двойник проходит гейт событием `AutoApprovedByRule` (аренда b-1, залог 30 000), выше — ждёт менеджера.
- **Модель не решает.** `assess_damage` — оценка (ADR-012). Удержание залога всегда идёт через менеджера (C004), при любой оценке.
- **Бизнес без реализации тоже модель.** drift даёт 20 WARN `not_implemented` и ни одной ошибки. Двойник проигрывает процессы с допущением «реализовано» и печатает его. С `--as-is` каждый процесс честно блокируется на Static Guard.

## Образец событий

`events.sample.json` — журнал двойника, две аренды в одном журнале (команда `make twin` с ключом `--events examples/equipment-rental/events.sample.json`):
- **b-1:** бронь → выдача → возврат без повреждений; залог 30 000 ниже порога → `AutoApprovedByRule`;
- **b-2:** бронь → выдача → возврат с повреждением → `HumanGateRequested` / `Claimed` / `Resolved` менеджером → `DepositWithheld`, единица в `repair`.

Сценарии — `twin-scenarios.json`.

## Не подтверждено

- C005 (проверка мастером после ремонта) — со слов сотрудника, в регламенте не найдено; процесс `repair_cycle` поэтому planned.
- Порог 50 000 ₽ и правило удержания — со слов владельца; формального регламента нет.
- Пример собран как демонстрация инструмента: реальный пункт проката не обследовался.
