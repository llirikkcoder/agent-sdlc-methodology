# Методология разработки систем с ИИ-агентами

Softoscope (пять слоёв модели) + Event Sourcing (память и аудит) + SDLC Pipeline (spec-first, гейты, человек в контуре).

Исходная постановка — `source/00-ishodnaya-specifikaciya-2026-10-25.md` (не правится). Этот репозиторий превращает её в проверяемую методологию: схемы, правила, инструменты и три контрастных примера.

## Зачем

Агент, которому систему объясняют абзацами промпта, догадывается: какой инструмент подходит, можно ли это откатить, нужен ли человек. Методология убирает догадки: система описана **данными** в пяти слоях, каждое действие оставляет **событие**, каждое исполнение идёт через **конвейер** с детерминированными гейтами. Агент либо знает, что делать, либо останавливается с именованной дырой (`MissingCapabilityError`) — третьего нет.

## Главное свойство: ядро универсально

Ядро (`schemas/`, `tools/`, `docs/01–04`, `docs/06`) не знает ни одной предметной области. Домен подключается только как данные: `purpose.json`, `domain.json`, `processes.json`, `capabilities.json`, `implementation.json`. Проверка — три непохожих примера в `examples/` и сторож `tools/check_core_purity.py`: доменное слово в ядре ломает сборку.

| Пример | Домен | Чем контрастен |
|---|---|---|
| `examples/regulated-document-qa/` | вопросно-ответная система по регулируемой документации: поиск по корпусу, модель-оценщик, очередь проверки человеком, журнал аудита | нет MCP: возможности — HTTP-маршруты, узлы графа, функции; условный гейт по оценке модели; производные состояния; заполнено по реальному коду, обезличено |
| `examples/ai-office-sales/` | операционные процессы продаж (домен исходника) | чистый MCP: возможности — инструменты сервера; ограничения, которые проверяет сам инструмент; намеренная дыра `send_invoice` как демонстрация `MissingCapabilityError` |
| `examples/agent-delivery/` | цикл поставки параллельными агентами (плагин anchor) | методология описывает собственный цикл поставки: возможности — CLI-скрипты, сверка с живым кодом (`make drift-anchor`); агент сливает сам по гейтам (ADR-019) |

## Для кого и как читать

- **Архитектор / владелец продукта** — `docs/01-softoscope.md` (что описывать и по каким правилам), затем README примера, ближайшего к вашему домену.
- **Разработчик** — `docs/03-sdlc-pipeline.md` (как изменения проходят гейты), `docs/01` раздел «Drift», `tools/`.
- **Тот, кто пишет агента** — `docs/04-mcp-scope-interface.md` (что агент спрашивает у модели) и `docs/02-event-sourcing.md` (что он обязан записывать).
- **Аудитор** — `docs/02-event-sourcing.md` (контракт события, проекции), `docs/06-glossary.md`.
- **Команда RAG-систем** — `docs/05-rag-as-special-case.md`: retrieval, генерация, судья и эскалация как обычные шаги и гейт.

  05-rag-as-special-case.md    — RAG в терминах методологии (не часть ядра)

  validate.py                  — схемы + межслойные правила (ссылки, гейты, события)

Почему такая структура, а не предложенная «docs по модулям + schemas + examples + tools» один к одному: модули исходника сохранены (01–04), но добавлены **глоссарий и RAG как отдельные документы** (чтобы RAG-слова не просачивались в модули ядра), **`open-questions.md` отдельно от ADR** (сводная таблица развилок с позициями и ссылками на ADR-010…017), и **README в каждом примере** с таблицей «что откуда взято» и списком «не подтверждено» — без этого пример нельзя отличить от выдумки.

## Быстрый старт

```bash
make check                                   # валидация (два валидатора), drift всех примеров, чистота ядра, тесты
make drift-strict                            # runtime Static Guard: planned-привязки и unconfirmed critical-ограничения — ERROR
make test                                    # 35 тестов ядра (входит в make check)
make drift-anchor ANCHOR_REPO=/путь/к/anchor  # пример agent-delivery против живого кода anchor
python3 tools/drift.py <модель> --json | python3 tools/holes_to_tasks.py - --emit bd   # дыры → команды трекера
make demo                                    # runtime на примере ai-office с моками: блокировка, гейт, человеческий шаг
python3 -m softoscope.mcp_server examples/ai-office-sales   # MCP-сервер scope_* по stdio
python3 tools/validate.py examples/regulated-document-qa
python3 tools/drift.py examples/ai-office-sales --strict
python3 tools/drift.py <модель> --repo /path/to/source-repo   # сверка привязок с кодом, только чтение
```

Требуется Python 3.11+. Пакет `jsonschema` необязателен: без него работает встроенный валидатор.

## Как применить к новому домену

1. **Скопируйте каркас.** `mkdir examples/<domain>` и пять файлов с одним `system_id` (можно взять любой пример и вычистить).
2. **Слой 1.** Напишите `purpose` в два предложения, перечислите роли (кто решает — `may_approve: true`), запишите жёсткие ограничения с `enforcement`. Всё, что со слов, — `status: unconfirmed`.
3. **Слой 2.** Сущности с идентификатором; у тех, что живут жизненным циклом, — состояния и переходы. Отметьте `sensitive` атрибуты.
4. **Слой 3.** Процессы по триггерам; шаги с исполнителем и ролью; на шагах агента — `capability_id` и `transition`. Запустите `tools/validate.py`: он скажет, где обязателен гейт.
5. **Слой 4.** Опишите каждую возможность, на которую сослались шаги: `kind`, `effect`, `idempotency`, роли, контракт. Необратимое — `human_gate_required: true`.
6. **Слой 5.** Привяжите возможности к коду или инструментам, с `evidence` и датой. Нет реализации — `status: planned`, не выдумывайте.
7. **События.** Составьте `events.sample.json` на один сквозной сценарий с гейтом и нарушением ограничения; валидатор проверит ссылки и чувствительные поля.
8. **Прогоните** `tools/drift.py <dir>` и, если есть код, `--repo`. Дыры — это задачи на цикл поставки, а не повод править модель под код.
9. **README примера**: откуда взято, что не подтверждено, чем домен проверяет ядро. Если для домена понадобилось новое поле в `schemas/` — остановитесь и проверьте, не доменное ли оно (`make purity`).

## Что проверено запуском

- `make check`: обе валидации (с `jsonschema` 4.26 и встроенным валидатором) дают одинаковый результат — 0 ошибок на всех трёх примерах; drift без ошибок (WARN: намеренные дыры `send_offer`/`send_invoice`, неподтверждённое C007); чистота ядра — 0 доменных слов.
- `make drift-strict` на regulated-document-qa показывает блокировку: C007 (critical, unconfirmed) → ERROR для двух процессов (ADR-017).
- `make test`: 35 тестов — уровни `unconfirmed` в `--strict` (ADR-017), дыры → задачи, порог и `AutoApprovedByRule`, гейт и роли, Static Guard (planned, unconfirmed, нет исполнителя), retry/escalate/abort, `llm_step` без модели, маскирование, пересборка проекций из JSONL, MCP по stdio.
- Негативные тесты по ADR-010/011/015: условный гейт на необратимом без порога, `system_level` без гейта, событие `llm_step` без `metadata.model` — ловятся валидатором.
- `drift.py examples/regulated-document-qa --repo <закрытый код>` на 25.10.2026: 0 расхождений с кодом; негативный тест с подменёнными символами, маршрутом, узлом графа, путём и классом таблицы — все пойманы. Пример обезличен: имена репозитория, модулей и таблиц заменены, поэтому в этом репозитории сверка с кодом не воспроизводится.
- Негативный тест валидатора: шаг агента на необратимой возможности без гейта и ссылка на несуществующую возможность — обе ошибки пойманы обоими валидаторами.

- `make drift-anchor` против anchor `a2ef20e` (26.10.2026): 0 расхождений; негативный тест с переименованными функциями и удалённым скриптом — все пойманы.

Что не проверено: привязки `mcp_tool` сверены со списком инструментов сервера, а не с его кодом; MCP-сервер `scope_*` проверен тестами по stdio, но не подключён к реальному агенту.
