# Модуль 3. SDLC Pipeline: конвейер исполнения и контроля

Исходная спецификация описывает один конвейер «от промпта до изменений». На практике это два разных цикла с общим механизмом гейтов (ADR-007):

- **Цикл исполнения (runtime)** — агент выполняет экземпляр процесса из слоя 3, порождая события.
- **Цикл поставки (delivery)** — команда (люди и агенты) меняет модель и код: сначала слои, потом реализация, через сторожей качества.

Оба цикла spec-first: ничего не исполняется и не пишется без того, чтобы это было описано в слоях.

## Цикл исполнения

```
Intake → Spec & Scope → Static Guard → Plan → Execute (шаг за шагом, события, гейты) → Verify → Close
```

### 0. Intake
Входящая задача сопоставляется с процессом слоя 3 по `trigger`. Нет подходящего процесса — задача не исполняется, а возвращается человеку как запрос на изменение модели (цикл поставки). Агент не изобретает процесс на ходу.

### 1. Spec & Scope
Агент читает слои 1–3 через `scope_*` (модуль 4): назначение и ограничения, сущность-агрегат и её состояния, карту шагов. Результат — список шагов с ролями, переходами, гейтами.

### 2. Static Guard
Детерминированная проверка до любого действия:
- для каждого шага агента/системы есть возможность (слой 4) и её привязка `status: implemented` (слой 5) — иначе **`MissingCapabilityError`**;
- правила гейтов выполнены (валидатор слоёв);
- ограничения `pre_check`, относящиеся к процессу и его возможностям, известны агенту (список прикладывается к плану).

`MissingCapabilityError` — это не исключение в логе, а событие `CapabilityMissing` + остановка процесса до решения человека. Структура:

```json
{
  "process_id": "…", "step_id": "…", "capability_id": "…",
  "reason": "not_declared | not_bound | not_implemented | stale | role_mismatch",
  "binding_status": "planned",
  "suggested_action": "описать возможность | реализовать | обновить слой 5 | выдать роль"
}
```

Смысл: агент не должен «догадываться», как выполнить шаг, если инструмента нет. Он должен остановиться и назвать дыру.

### 3. Plan
Граф исполнения: шаг → возможность → входы из проекций/предыдущих шагов. Для каждого шага заранее известно: эффект, нужен ли гейт и кто утверждает, какой переход сущности ожидается. План записывается в `ProcessInitiated.payload`.

### 4. Execute
Для каждого шага:
1. `StepRequested` (с `capability_id`, входами без чувствительных данных).
2. Если `human_gate.required` и условие гейта выполнено — `HumanGateRequested`, процесс ждёт `HumanGateResolved`. `rejected` → по `on_failure` (обычно `abort` или возврат на предыдущий шаг).
3. Проверка `pre_check`-ограничений возможности; нарушение → `ConstraintViolated`, шаг не вызывается.
4. Вызов возможности. Успех → `StepCompleted` и, если шаг объявил `transition`, `EntityTransitioned`. Ошибка → `StepFailed` → `on_failure`: `retry` только при `idempotency != none`; `escalate` → гейт; `skip`; `abort` → `ProcessAborted`.

Человеческий шаг (`actor: human`) исполняется человеком; агент ждёт события, которое порождает интерфейс или интеграция. Агент никогда не делает шаг человека за него.

### 5. Verify
После каждого шага и в конце:
- проекция `EntityState` сверяется с хранилищем (слой 5) — `post_check`;
- `post_check`-ограничения слоя 1;
- цели слоя 1 с `metric` — если измеримы на экземпляре.
Расхождение → `ConstraintViolated` или `StepFailed`, процесс не считается завершённым.

### 6. Close
`ProcessCompleted` с итогом; экземпляр уходит из `ProcessInstance` в историю.

## Human-in-the-loop

Гейт — единственный способ, которым человек входит в автоматический процесс, и он описан данными, а не промптом:
- откуда берётся — правило гейта (модуль 1): необратимость, политика возможности, ограничение `enforcement: gate`;
- кто решает — `approver_role` с `may_approve`;
- когда — `condition` (только для политик и ограничений; для необратимых действий — всегда);
- как выглядит для человека — проекция `PendingGates` (очередь с возрастом, SLA, причиной);
- как фиксируется — `HumanGateResolved` с `actor.id` (не «system»).

Эскалация (`on_failure: escalate`, `reason: low_confidence`) — тот же гейт, только причина другая. Отдельного механизма «спросить человека» в ядре нет: это всегда событие и очередь.

## Цикл поставки

```
Постановка (человек) → Изменение слоёв → Static Guard (валидация + drift) → Реализация → Verify (checks) → Merge по гейтам → Drift по расписанию
```

1. **Изменение начинается со слоёв**, не с кода. Новый шаг — сначала в `processes.json` (можно с `status: planned` у процесса), новая возможность — в `capabilities.json`, и только потом код и привязка в слое 5.
2. **Static Guard**: `tools/validate.py` (схемы + семантика) и `tools/drift.py` — обязательные сторожа в CI. Красный валидатор блокирует слияние.
3. **Реализация**: код пишется под контракт возможности (`inputs`/`outputs`, `effect`, `idempotency`). Если в ходе реализации контракт оказался неверен — правится слой 4 в том же изменении.
4. **Verify**: `checks[]` слоя 5 — по ступеням `stage`, от дешёвой к дорогой:
   - `on_edit` — хуки в сессии агента при правке или команде;
   - `static_guard` — проверка модели;
   - `verify` — тесты и smoke;
   - `pre_merge` — гейты слияния.

   Чем больше очевидных ошибок поймано на ранней ступени, тем меньше их доезжает до гейтов слияния и до человека. Обязательное выносится в хуки, а не в текст правил. Медленное (сборка, длинные тесты) запускается в фоне или через очередь тяжёлых команд. Результаты прикладываются к изменению; пропущенные проверки отмечаются отдельно от прошедших.
5. **Merge**: при зелёных гейтах агент-разработчик сливает сам — поверх свежего `main`, ровно проверенный коммит (ADR-019). Человек решает в постановке задачи. Перед слиянием человек нужен только в исключениях: правка ядра модели (`effect`, `human_gate_required`, `system_level`, ограничения слоя 1 — всегда с явным решением в ADR проекта), миграции и другие `system_level`, выкат во внешний мир.
6. **Drift по расписанию** против живого репозитория: `python3 tools/drift.py <модель> --repo <код>`; находки — событие `DriftDetected` и задача.

## Мост между циклами: агент-разработчик

Агент-оператор (исполняет процессы) и агент-разработчик (меняет код и модель самой системы) — разные роли с разными правами, и в один конвейер они не сливаются (ADR-013). Агент-разработчик проходит цикл поставки как исполнитель процесса: нашёл дыру (`CapabilityMissing`, `DriftDetected`) → подготовил изменение кода **и** слоёв → открыл запрос на слияние → прогнал гейты поверх свежего `main` → слил сам (ADR-019; ADR-013 требовал ревью человеком на каждом слиянии, на практике это сводилось к напоминаниям). Согласие человека — поставленная задача; постановка может прямо запретить слияние. Без человека не сливается и не выполняется: правка ядра модели, миграции, конфигурация и права (`system_level: true`), выкат, который публикует или тратит деньги, а также изменения, которые надо проверять вместе (их сводит координатор по тем же гейтам). Правка кода при зелёных гейтах — не системное действие.

### Стык с исполнителем поставки: гейты и задачи

Методология не задаёт, как именно агенты делят работу. Одна из реализаций — плагин anchor: тема, дерево, воркер, слияние по гейтам. Он описан данными в `examples/agent-delivery`. Стык держится на двух вещах, и обе работают в одну сторону:
- **Гейты.** Список гейтов слияния лежит в репозитории (в anchor это `.anchor/gates`) и включает проверку модели: `validate`, `drift`, чистоту ядра. Гейты берутся из `main`, а не из проверяемой ветки.
- **Дыры как задачи.** `tools/holes_to_tasks.py` превращает отчёт `drift.py --json` или события `CapabilityMissing`/`DriftDetected` из журнала в задачи с устойчивым ключом `drift:<причина>:<процесс>:<шаг>:<возможность>`. Повторный прогон не плодит дублей (`--skip-keys`). Инструмент только печатает; в трекер пишет тот, кто его вызвал.

Обратной синхронизации из трекера в модель нет: закрытая задача модель не меняет. Модель меняет запрос на слияние, прошедший гейты.

### Регулярные задачи агента

Агента запускают не только из чата: по расписанию или по событию (scheduled task агента, задача CI после слияния). Для методологии это обычный процесс слоя 3 с `trigger.kind: schedule` или `event`. Описывается и проверяется он так же, как любой другой. Два типовых примера описаны в `examples/agent-delivery` со статусом `planned`:
- **drift по расписанию** — `drift.py --repo --json` со снимком исходника, затем `holes_to_tasks.py`: задачи заводятся только по новым дырам;
- **документация после слияния** — агент сверяет документацию с изменением и, если она отстала, ставит тему на её обновление. Сама правка документации проходит цикл поставки, как любая другая.

### Доставка правил слоями

Правила, по которым работают агенты, доставляются четырьмя слоями. Чем выше слой, тем меньше у агента возможности обойти правило:

| Слой | Что в нём | Пример |
|---|---|---|
| Репозиторий | модель (пять слоёв), `checks[]`, гейты слияния, правила и навыки агента — коммитятся вместе с кодом | `examples/<система>/`, `.anchor/gates` |
| Плагин | общее для многих репозиториев: команды, навыки, хуки, скрипты обвязки | anchor |
| Управляемые настройки | то, что нельзя выключить из сессии: ограда воркера, запреты команд, права | `worker-guard`, хук запрета деструктивных команд |
| Инфраструктура | CI, серверные проверки, защита ветки `main` | гейты в CI, `--match-head-commit` |

Правило записывается в самый нижний слой, где его достаточно, а обязательное поднимается до слоя, который агент не может обойти. Правило, которое держится только на тексте промпта, исполняется до первого забытого раза; ADR-019 появился ровно так.

### Static Guard и неподтверждённые ограничения

Ограничение слоя 1 со `status: unconfirmed`:
- `critical` — runtime Static Guard (`drift.py --strict`) **блокирует** исполнение процессов, к которым оно применимо, до подтверждения человеком; в цикле поставки это предупреждение (модель можно сливать, исполнять нельзя);
- `high` — предупреждение в strict, пометка в поставке;
- `medium` — пометка (ADR-017).

## Quality gates, сводно

| Гейт | Чем | Когда | Красный блокирует |
|---|---|---|---|
| Хуки агента | `checks[]` со `stage: on_edit` | правка или команда в сессии агента | да, до действия |
| Схемы слоёв | `validate.py` (схемный уровень) | каждое изменение слоёв | да |
| Семантика слоёв | `validate.py` (ссылки, правила гейтов, события) | каждое изменение слоёв | да |
| Drift модели | `drift.py` | каждое изменение слоёв/кода | да (ERROR); WARN — в `--strict` |
| Runtime Static Guard | `drift.py --strict` / `scope_check_drift {strict: true}` | перед каждым исполнением процесса | да, включая `planned`-привязки и `unconfirmed` critical-ограничения |
| Drift против кода | `drift.py --repo` | по расписанию и перед релизом | да |
| Чистота ядра | `check_core_purity.py` | изменения в `schemas/`, `tools/`, `docs/` | да |
| Сторожа кода | `checks[]` слоя 5 | реализация | да |
| Слияние | агент по зелёным гейтам выше, ровно проверенный коммит (ADR-019) | конец задачи поставки | красный гейт — слияния нет |
| Человек | постановка; исключения ADR-019; `HumanGateResolved` | по правилу гейта | да |

Исполняемое воплощение цикла исполнения — `softoscope/runtime.py` (модуль 7).

## Чего конвейер не делает

- Не подбирает возможность по смыслу, если `capability_id` не совпал: это дыра, а не повод для догадки.
- Не выполняет шаг человека.
- Не пропускает необратимое действие по «уверенности» модели: уверенность — причина для гейта `low_confidence`, а не замена гейта. Автоматическое прохождение гейта возможно только по детерминированному порогу ограничения (`AutoApprovedByRule`), никогда по вердикту модели (ADR-010, ADR-012).
- Не правит слой 5 автоматически по коду: привязка — утверждение человека, подтверждённое `evidence`.
