# Модуль 8. Оцифровка: описание классами, карта, цифровой двойник

Пять слоёв (модуль 1) можно писать руками в JSON, а можно классами Python. Второй путь даёт проверку ссылок при импорте, наследование и порог прямо из атрибута. Результат один и тот же: пять файлов слоёв, которые проходят валидатор (ADR-021).

```
описание.py ──build──▶ purpose/domain/processes/capabilities/implementation.json ──▶ validate, drift, scope_*, runtime
     ▲                                   │
     └─────────────decompile─────────────┤
                                         ├──map──▶ сводка + схемы процессов + автоматы (Markdown, Mermaid)
                                         └──twin─▶ прогон процессов на заглушках: журнал, гейты, состояния
```

## Как оцифровать систему

1. **Начать с готового или с пустого.** Если модель уже есть в JSON — `python3 tools/digitize.py decompile <каталог> --out model.py`. Если нет — новый `model.py` по образцу `examples/equipment-rental/model.py`.
2. **Описать слой за слоем** — те же правила, что в модуле 1. Чего нет в коде — `Binding(..., status="planned")`, что со слов — `status="unconfirmed"` у ограничения.
3. **Собрать:** `python3 tools/digitize.py build model.py --out <каталог>`. Невалидная модель не записывается: ошибки валидатора печатаются, файлы остаются прежними.
4. **Посмотреть:** `python3 tools/digitize.py map <каталог или model.py> --out map.md`.
5. **Проиграть:** `python3 tools/digitize.py twin <каталог или model.py> --scenario s.json --chain p1,p2,p3@агрегат`.
6. **Закоммитить** `model.py` и пять файлов; добавить каталог в `DESCRIBED` в `Makefile`, чтобы `make check` ловил расхождение.

## Словарь описания

| Слой | Объект | Имя берётся из | Пример |
|---|---|---|---|
| 1 | `System(system_id, spec_version, purpose, goals=[Goal(...)], as_of=...)` | — (ровно один в модуле) | |
| 1 | `Role.human / .agent / .system(описание, may_approve=)` | переменной | `manager = Role.human("…", may_approve=True)` |
| 1 | `Constraint(правило, severity=, enforcement=, entities=/capabilities=/processes=, threshold=)` | переменной (`C001`) | `threshold=("Deposit.amount", ">", 50000, "RUB")` |
| 2 | `class X(Entity)`, `Attr(тип, required=, sensitive=, enum=)`, `State(initial=, terminal=)` | класса, атрибута | `held.to(refunded, actor="agent", reversible=False, guard=C001)` |
| 2 | `Event(сущность, описание)` | переменной | `DepositRefunded = Event(Deposit, "…")` |
| 2 | `Relation(имя, цель, cardinality)`, `invariants = [...]` | — | |
| 3 | `class Y(Process)`: `name`, `trigger = Trigger.<kind>(...)`, `aggregate` | класса (`DamagedReturn` → `damaged_return`) | |
| 3 | `Step.agent / .human / .system(название, role=, capability=, gate=, transition=, emits=, on_failure=)` | атрибута | `transition=Deposit.held.to(Deposit.refunded)` |
| 3 | `Gate(approver=, constraint=, condition=)` | — | `condition=Deposit.amount > 50000` |
| 4 | `Capability(название, kind=, effect=, touches=, constraints=, compensation=)` | переменной | `human_gate_required` по умолчанию — необратимое или `system_level` |
| 5 | `Binding(возможность, status=, evidence=, path=, symbol=, route=(метод, путь), mcp=(сервер, инструмент))` | — | список `bindings = [...]` в модуле |

Наследование:
- `class Tracked(Entity, abstract=True)` — база, в слой не попадает, атрибуты наследуются;
- `class DamagedReturn(RentalReturn)` — процесс-наследник: шаги базы в том же порядке, шаг с тем же именем заменяется на месте, новые идут в конце.

Поля сверх словаря передаются как `**extra` (у сущности и процесса — атрибут `extra`), поэтому `decompile` → `build` возвращает модель без потерь даже с полями, которых описание не знает.

## Карта модели

`digitize map` строит документ из пяти слоёв и дыр drift:
- сводка — что описано в каждом слое, сколько дыр, таблица процессов: запуск, шагов, человеческих шагов, гейтов, дыр, статус;
- схема каждого процесса: прямоугольник — агент, параллелограмм — человек, двойная рамка — система; ромб — гейт с утверждающим, условием и причинами по правилу гейта (модуль 1); штриховая рамка — у шага нет implemented-привязки; пунктирная петля — `on_failure`; `⇒` — доменные события, которые пишет шаг. Шаг с `terminal: true` (ветка в конец процесса, например уточнение вместо ответа) ведёт сразу в «завершён»; условие `condition` подписано на каждом входящем ребре;
- `--process a,b,c` — несколько процессов одной темы на одной схеме, каждый в своей рамке (разные входы в одно хранилище, переиндексация и удаление);
- автомат каждой сущности с состояниями: кто переводит, необратимость, страж.

## Цифровой двойник

Двойник запускает **тот же runtime** (модуль 7). Возможности заменены заглушками, человек действует по сценарию. Поэтому всё, что двойник показывает, верно и для настоящего исполнения:
- Static Guard;
- правило гейта и порог (`AutoApprovedByRule` ниже порога, `HumanGateRequested` выше);
- проверка перехода по автомату до вызова;
- `on_failure`, доменные события, маскирование.

Сценарий — JSON. Без `--process` и `--chain` он задаётся как `{процесс: сценарий}` или `{"процесс@агрегат": сценарий}`. Поля сценария:

| Поле | Что задаёт |
|---|---|
| `inputs` | входы процесса (`ProcessInitiated.payload.inputs`), в том числе id сущностей (`deposit_id`) |
| `entities` | `"Сущность:id" → атрибуты`: из них берётся значение порога |
| `outputs` | `capability_id → что вернёт заглушка` |
| `decisions` | `step_id → approved/rejected` для гейтов (по умолчанию approved) |
| `human_outputs` | `step_id → результат человеческого шага` |
| `fail` | `capability_id`, которые откажут (`CapabilityError` → `on_failure`) |

Заглушка сама выдаёт идентификаторы сущностей, которых касается возможность (`deposit_id` и т. п.), если их нет во входах. Иначе runtime не узнал бы текущее состояние сущности.

Цепочка (`--chain booking_request,equipment_issue,rental_return@b-1`) прогоняет процессы друг за другом в общем журнале. Состояния сущностей переходят из процесса в процесс, поэтому пропущенный или лишний переход виден сразу. `--events файл` сохраняет журнал как образец событий; так получен `examples/equipment-rental/events.sample.json`.

Допущения печатаются в начале вывода и есть в `--json`:
- по умолчанию возможности без реализации считаются реализованными;
- `--as-is` убирает это допущение: процесс с дырой блокируется, как в жизни;
- `--assume-confirmed` снимает блокировку по неподтверждённым critical-ограничениям.

## Что двойник находит, а валидатор нет

Валидатор проверяет каждый шаг по отдельности: переход есть в автомате, гейт стоит, ссылки целы. Двойник проверяет **последовательность**: дойдёт ли сущность до состояния, из которого следующий шаг разрешён. Прогон всех активных процессов существующих примеров 27.10.2026 нашёл два таких расхождения, они описаны в README примеров (`examples/ai-office-sales`, `examples/agent-delivery`, раздел «Находки цифрового двойника»). Исправлять ли их, решает владелец домена: это данные примера, а не ядро.
