# ADR-018. Границы эталонной реализации

**Статус.** Принято 25.10.2026 (Кирилл: «приступаем к реализации» — MCP-сервер scope_* и runtime, оба в этом репозитории).

**Контекст.** Методология описана документами, схемами и сторожами. Чтобы проверить, что модули 2–4 исполнимы и что ядро действительно не знает домена, нужна реализация, но не продукт.

**Решение.**
1. Пакет `softoscope/` в этом репозитории, только стандартная библиотека (как tools/, ADR-009). MCP-транспорт — stdio JSON-RPC 2.0, написан вручную (initialize, ping, tools/list, tools/call), без SDK.
2. Возможности исполняют **исполнители**, которые подключает реализация; runtime не содержит ни одного клиента к внешним системам. Нет исполнителя у `implemented`-возможности — это дыра Static Guard (`not_bound`), а не повод для подбора.
3. Единственный источник истины — журнал событий; проекции пересобираются с нуля перед каждым решением. Снимков нет.
4. Правила ядра (гейт, порог, переходы, маскирование) живут в `softoscope/model.py` и повторяют `tools/validate.py`; модель загружается только после зелёного валидатора.
5. Тесты ядра — на синтетической модели без домена (`tests/fixture_model.py`); доменные примеры — только в демонстрациях внутри `examples/`.
6. Чистота ядра (`check_core_purity.py`) распространяется на `softoscope/*.py` и `docs/07`.

**Почему так.** Эталон должен доказывать свойства методологии (spec-first, гейт по данным, журнал как истина), а не конкурировать с фреймворками. Любая зависимость или встроенный клиент сделали бы ядро «знающим» транспорт или домен.

**Последствия.** `make test` в `make check`. Продуктивная реализация берёт `softoscope/` как референс контрактов, а не как библиотеку.
