# ADR-006. Уровни и причины дыр в drift

**Статус.** Принято; уточнено ADR-020 (26.10.2026): Python-код сверяется по реестру `ast`, добавлены дыра `unmodeled` (всегда WARN) и снимок исходника.

**Контекст.** Исходник: «drift.sh проверяет, совпадает ли объявленный процесс с реальным наличием кода». Нужно определить, что именно считать расхождением и насколько оно блокирует.

**Решение.** Дыра имеет `reason` и `level`:

| reason | level по умолчанию | блокирует |
|---|---|---|
| `not_declared` (шаг → нет возможности) | ERROR | да |
| `not_bound` (возможность → нет привязки) | ERROR; WARN для `planned`-процесса | да / нет |
| `not_implemented` (привязка не `implemented`) | WARN; ERROR в `--strict`; INFO для `planned`-процесса | в strict |
| `stale` (привязка не найдена в коде, `--repo`) | ERROR | да |
| `orphan` (привязка к несуществующей возможности) | ERROR | да |
| `unused` (возможность без шагов) | INFO; WARN, если и не привязана | нет |
| `unverifiable` (`mcp_tool` без пути) | INFO | нет |
| `unmodeled` (в коде есть маршрут, узел графа или таблица, которых нет в слое 5; ADR-020) | WARN, и в `--strict` тоже | нет |

Код возврата 1 при любом ERROR.

**Почему два режима.** В цикле поставки допустимо описать возможность раньше кода (`planned`) — иначе spec-first невозможен. Но перед релизом и в runtime Static Guard `--strict` превращает это в блокер: исполнять процесс с `planned`-шагом нельзя.

**Проверка по коду** намеренно простая (регулярные выражения по пути/символу/декоратору маршрута/`add_node`/`__tablename__`), чтобы работать без парсеров языка и без установки проекта. Ложные «stale» возможны при экзотическом синтаксисе — тогда уточняется `location`, а не ослабляется проверка.
