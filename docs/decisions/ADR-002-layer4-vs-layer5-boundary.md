# ADR-002. Граница между слоем 4 и слоем 5

**Контекст.** В исходнике слой 4 содержит `mcp_server` и `tool_name`, а слой 5 описан одной фразой «статическая привязка к коду». Непонятно, где контракт, а где адрес.

**Решение.** Слой 4 — **контракт** возможности: идентификатор, смысл, `kind`, `effect`, роли, входы/выходы, предусловия, идемпотентность, ограничения. Слой 5 — **адрес** реализации: путь, символ, маршрут, узел графа, `{server, tool}` для MCP, команда CLI, флаг, статус, чем подтверждено, когда.

Критерий: **если переименование файла, маршрута или инструмента меняет поле — это слой 5.** Если меняется смысл действия или его эффект — слой 4.

**Следствия.**
- Имя возможности не обязано совпадать с именем инструмента (`move_deal_stage` ↔ `update_deal_status`); это норма, а не drift.
- У одной возможности может быть несколько привязок (маршрут + функция + узел графа).
- Рефакторинг трогает только слой 5; процессы и контракты переживают переезд с HTTP на MCP без правок.
- Drift сравнивает слой 5 с кодом, а слои 3–4 — со слоем 5; он никогда не сравнивает слой 4 с кодом напрямую.
