# ADR-021. Объектное описание системы и цифровой двойник

**Статус.** Принято 27.10.2026 (Кирилл: «давай соберём новый инструмент, который с помощью ООП может оцифровать любую бизнес-систему и представить все её процессы в виде цифровой модели»). Не меняет ни одного правила методологии: только способ писать слои и смотреть на них.

**Контекст.** Пять слоёв пишутся руками в JSON (ADR-001). Для системы на два десятка процессов это неудобно:
- ссылки строковые: опечатка в `capability_id` или роли видна только валидатору;
- общее не выносится: одинаковые атрибуты сущностей и почти одинаковые процессы копируются;
- модель трудно увидеть целиком — нет картинки процессов и автоматов;
- нельзя «проиграть» процесс до того, как появилась реализация: runtime требует исполнителей и implemented-привязки.

**Решение.**
1. **Объектное описание** (`softoscope/oop.py`). Модуль Python, где система описана классами и объектами:
   - сущность — подкласс `Entity` (атрибуты `Attr`, состояния `State`, переходы `состояние.to(...)`);
   - процесс — подкласс `Process` (шаги `Step` в порядке объявления);
   - роль, ограничение, возможность, событие, привязка — объекты `Role`, `Constraint`, `Capability`, `Event`, `Binding`;
   - имена берутся из имён переменных, классов и атрибутов; ссылки — объекты, поэтому опечатка падает при импорте;
   - наследование: абстрактная база (`abstract=True`) отдаёт атрибуты и шаги, наследник заменяет шаг по имени на его месте;
   - порог и условие гейта — выражение `Сущность.атрибут > значение`.
2. **Источник истины не меняется.** Описание компилируется в те же пять файлов (`tools/digitize.py build`), они проходят тот же валидатор и коммитятся. Если у примера есть `model.py`, `make check` сверяет его с файлами (`build --check`): правка одного без другого ломает сборку. `decompile` переводит любую готовую модель в описание без потерь — круг проверен тестом на всех примерах.
3. **Карта модели** (`softoscope/process_map.py`, `digitize map`): сводка по пяти слоям, схема каждого процесса (исполнитель, возможность и класс эффекта, гейт ромбом с утверждающим и условием, переход сущности, шаги без реализации — штриховой рамкой) и автомат каждой сущности, в Markdown + Mermaid.
4. **Цифровой двойник** (`softoscope/twin.py`, `digitize twin`). Это не второй исполнитель, а тот же runtime (ADR-018) с заглушками вместо возможностей и человеком по сценарию:
   - Static Guard, гейты, пороги, переходы, `on_failure`, события — настоящие;
   - журнал проходит схему события;
   - цепочка процессов над одним агрегатом идёт в общем журнале, поэтому состояния сущностей переходят из процесса в процесс.
5. **Допущения двойника всегда названы и никогда не пишутся в модель:**
   - «возможность без implemented-привязки считается реализованной» — включено по умолчанию, выключается `--as-is`;
   - «неподтверждённое ограничение считается подтверждённым» — выключено по умолчанию, включается `--assume-confirmed`.

   Двойник работает на временной копии слоёв.

**Почему так.** Классы дают то, чего нет в JSON: проверку ссылок интерпретатором, наследование и вычисляемые выражения. Но если сделать Python источником истины, методология станет зависеть от языка. Поэтому JSON остаётся контрактом, а Python — удобным способом его писать, с обратным ходом и сторожем расхождения. Двойник на настоящем runtime проверяет модель теми же правилами, что и жизнь: расхождение двойника с runtime было бы второй истиной.

**Последствия.**
- В ядре четыре модуля (`oop`, `decompile`, `twin`, `process_map`) и CLI `tools/digitize.py`; все под сторожем чистоты.
- Четвёртый пример `examples/equipment-rental` описан классами, кода у бизнеса нет (все привязки `planned`); `events.sample.json` получен прогоном двойника.
- `make described` (входит в `make check`), `make twin`.
- Двойник уже нашёл в существующих примерах расхождения процессов с автоматами слоя 2: они в README примеров, раздел «Находки цифрового двойника».
- Чего нет: рендер Mermaid в CI не проверяется (нет зависимости); описание пока только на Python.
