# Модуль 2. Event Sourcing: память и аудит

Каждое действие агента, решение человека и смена состояния сущности — событие в неизменяемом журнале. Текущее состояние чего угодно (процесса, очереди, сущности) — проекция, вычисленная из событий, и его всегда можно пересчитать.

Зачем это агенту: (1) агент не помнит — журнал помнит; (2) аудитор не верит — журнал показывает; (3) система упала — журнал восстанавливает.

## Контракт события

Схема — `schemas/event.schema.json`. Обязательные поля:

| Поле | Что | Пример |
|---|---|---|
| `event_id` | UUID события | `…-0001` |
| `event_type` | тип из базового каталога или `domain_events` слоя 2 | `HumanGateRequested` |
| `occurred_at` | ISO 8601 с зоной | `2026-10-25T12:00:20Z` |
| `sequence` | номер внутри агрегата (необязательно, но нужен для обнаружения пропусков) | `3` |
| `aggregate` | к чему относится поток: `{kind: process_instance | entity, type, id}` | `{process_instance, answer_question, msg-5e01}` |
| `actor` | кто: `{kind: agent | human | system, id, role}` | `{human, user_42, approver}` |
| `scope` | явные ссылки на модель: `system_id`, `process_id`, `step_id`, `capability_id`, `entity`, `constraint_id` | |
| `payload` | данные события; без чувствительных атрибутов открытым текстом | |
| `metadata` | `correlation_id` (обязателен), `causation_id`, `idempotency_key`, `schema_version`, `model {name, version, prompt_version}`, `trace` | |

Почему `scope` вместо поля `layer: 1..5` из исходной спецификации — `decisions/ADR-005-event-scope-instead-of-layer.md`: номер слоя выводится из того, на что ссылается событие, а ссылки проверяемы.

Правила:
- `correlation_id` один на всю цепочку «запрос → шаги → гейт → решение → ответ». Без него аудит восстанавливает связь по косвенным ключам.
- `causation_id` — `event_id` события или команды, вызвавшей это событие. Даёт причинный граф.
- `actor.kind = human` без `actor.id` — предупреждение: аудит не атрибутирован.
- `payload` не содержит атрибутов, помеченных `sensitive` в слое 2 (валидатор проверяет по `scope.entity`).
- Событие, порождённое моделью, несёт `metadata.model` (имя, версия, версия промпта) — иначе результат невоспроизводим.

## Базовый каталог событий

Эти четырнадцать типов знает ядро. Их имена нельзя занимать доменными событиями.

| Тип | Когда | Обязательно в scope / payload |
|---|---|---|
| `ProcessInitiated` | запущен экземпляр процесса | `process_id` |
| `StepRequested` | агент намерен выполнить шаг | `step_id`, `capability_id` |
| `StepCompleted` | шаг выполнен | `step_id`; результат в payload |
| `StepFailed` | шаг не выполнен | `step_id`; причина, `on_failure` |
| `HumanGateRequested` | шаг ждёт решения человека | `step_id`; `payload.approver_role`, причина |
| `HumanGateClaimed` | человек взял гейт в работу | `actor.kind = human`, `actor.id` |
| `HumanGateResolved` | человек решил | `payload.decision: approved | rejected`; `actor.kind = human` |
| `AutoApprovedByRule` | условный гейт пройден автоматически по порогу ограничения | `step_id`, `constraint_id`; `payload.attribute`, `payload.value`, порог (ADR-010) |
| `ConstraintViolated` | попытка нарушить правило слоя 1 | `constraint_id` |
| `EntityTransitioned` | сущность сменила состояние | `entity`; `payload.from`, `payload.to` (переход должен существовать в слое 2) |
| `ProcessCompleted` / `ProcessAborted` | экземпляр завершён / прерван | `process_id` |
| `CapabilityMissing` | Static Guard не нашёл работающей возможности для шага | `step_id`, `capability_id`; `payload.reason` как в drift |
| `DriftDetected` | плановая drift-проверка нашла расхождения | `payload.holes[]` |

Доменные события (`DraftGenerated`, `ItemShipped`, …) объявляются в `domain_events` слоя 2 с привязкой к сущности и используются в `emits` шагов. Всё остальное — в `payload` базовых типов, а не новыми типами: каталог растёт только когда появляется новый **класс** факта, а не новый домен.

## Проекции

Проекция — функция от последовательности событий. Ядро определяет четыре; домен добавляет свои тем же способом.

| Проекция | Из каких событий | Что отвечает |
|---|---|---|
| `ProcessInstance` | `ProcessInitiated`, `Step*`, `HumanGate*`, `Process*` | на каком шаге экземпляр, что ждёт, чем кончился |
| `PendingGates` | `HumanGateRequested` без парного `HumanGateResolved` | очередь решений человека — по ролям, с возрастом и SLA |
| `EntityState` | `EntityTransitioned` по `aggregate.id` | текущее состояние каждой сущности; сверяется с хранилищем слоя 5 (`post_check`) |
| `AuditTrail` | все события, фильтр по `scope`, `actor`, времени | ответ аудитору «кто, что, когда, на каком основании» |

`PendingGates` — это и есть «очередь на проверку человеком», как бы она ни называлась в домене. Реализация **может** хранить очередь первичной таблицей или сущностью слоя 2 с собственными статусами (взять, отклонить, переоткрыть) — требовать полной восстановимости из журнала от существующих систем и внешних трекеров нереалистично. Обязательное условие одно: **каждая смена состояния очереди порождает событие** (`HumanGateClaimed`, `HumanGateResolved`, `EntityTransitioned` по сущности очереди), чтобы проекция `PendingGates` и журнал сходились с таблицей (ADR-014).

## Идемпотентность

- **События**: `event_id` уникален; повтор записи с тем же `event_id` отбрасывается.
- **Команды**: `metadata.idempotency_key` — ключ команды (например, идентификатор сообщения, по которому ставится элемент очереди). Второе событие с тем же ключом в том же агрегате не записывается. Возможности с `idempotency: key` обязаны передавать ключ; с `idempotency: none` — безопасно вызываются только после проверки проекции.
- **Потребители**: проекция хранит последний применённый `sequence` по агрегату и игнорирует уже применённые события; пропуск в `sequence` — сигнал о потере.

## Восстановление и time-travel

1. Проекция повреждена или схема проекции изменилась — проекция пересобирается с нуля по журналу.
2. Нужно состояние на момент T — события до T.
3. Процесс упал посреди шага — по `ProcessInstance` виден последний `StepRequested` без `StepCompleted`; конвейер решает по `on_failure` шага: `retry` (повтор безопасен только при `idempotency != none`), `escalate` (гейт человеку), `abort`.
4. Снимки (snapshots) проекций допустимы как ускорение, но не как источник истины.

## Что хранить, чего не хранить

- Хранить: решения (гейты, включая автоматические `AutoApprovedByRule`), переходы, вызовы возможностей с `effect != read`, нарушения ограничений.
- Чтения (`effect: read`, кроме `llm_step`): только итоговый `StepCompleted` с агрегатом или хэшем полученных данных; `StepRequested` не обязателен. Иначе журнал превращается в шум (ADR-015).
- Шаги модели (`kind: llm_step` — судьи, классификаторы, генерация): **всегда полный лог** — `StepRequested` и `StepCompleted`, `metadata.model {name, version, prompt_version}` обязательны (валидатор: ошибка без `model`, предупреждение без `prompt_version`), вход и выход — по ссылке или хэшу в `payload`, если содержат чувствительные данные.
- Не хранить открытым текстом: чувствительные атрибуты, секреты, полные тексты, если их можно сослаться по идентификатору.

## Как это ложится на реализацию

Слой 5 описывает `event_sinks` — куда события пишутся в коде (таблица журнала аудита, лог). Если в коде журнал имеет другой формат (например, `{event_type, entity_id, changes[{field,before,after}], meta}`), в README примера пишется таблица соответствия контракту; ядро формат кода не диктует, но требует, чтобы отображение было взаимно однозначным по обязательным полям. Чего чаще всего не хватает в существующих журналах: `correlation_id`, `causation_id`, версия модели.
